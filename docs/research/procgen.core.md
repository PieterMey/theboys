# procgen

## Executive summary
For tonight, the approach that gives the most gameplay for the least code is a grid floor-plan generator: 1 m integer cells, thin walls on cell edges, a corridor lattice (every enclosed block is a ring, so loops are guaranteed), BSP-subdivided rooms inside the blocks, and one room/door graph that drives everything else (locks and keys, placement, culling, AI). The DunGen approach that Lethal Company uses (tiles snapped together by doorway sockets) and Unexplored's cyclic graph grammars both produce great levels. But they depend on hand-authored room prefabs or thousands of rules, and nobody on this project can author those in an editor. WFC (wave function collapse) gives poor control over connectivity and loops. All three are deferred. Locks and keys work as nested zones: each zone is a breadth-first "ball" grown on the room graph and gets exactly one keycard door; every other door on the zone border becomes rubble or a jammed door; the key for zone z goes in zone z-1, far from its lock (the Metazelda key-level idea). A small loop that collects keys and expands the reachable area proves every level can be finished. I built and tested this generator as a strict-TypeScript prototype in the scratchpad. A 64x48 m level takes 1.6 ms median, all 1000 test seeds produced valid, reproducible levels (0.4% needed one retry with a derived seed), and the result averages about 140 rooms, about 30 independent loops and 2 locked zones. The full layout is 22 KB as JSON (4.6 KB gzipped). So the server should generate it and broadcast it; the seed is kept for reproducing bugs and for cosmetic-only decoration. This avoids cross-browser floating-point drift: per the ECMAScript spec Math.sin/cos/exp are "implementation-approximated", and Firefox only uses the consistent fdlibm library when resistFingerprinting is on. Geometry is built per room or corridor from runs of wall edges, with corner posts at grid vertices and world-space UVs. That comes to about 10k triangles and 4.5 ms per level. Use one merged Mesh per space, InstancedMesh for props, and DunGen-style adjacency culling that also switches room lights on and off. One graphics catch: three.js r186's new VXGI (voxel global illumination) skips BatchedMesh, so don't use BatchedMesh for level geometry. Monster navigation, line of sight and hearing should run on the server over the same edge grid: A* takes 0.17 ms, a sight ray about 50 ns, and a door-aware sound flood 0.04 ms, and door state changes take effect immediately. navcat 0.4.1 (a pure-JS navmesh library that runs in Node) is the upgrade path; a navmesh for the same level takes 100-330 ms to build. Recommendation: implement the lattice+BSP generator, the zone/lock system, the placement rules and the edge-grid AI in a shared TS package tonight (facility theme, single floor), with a 1000-seed property test and PNG map renders. Add hospital/house presets, navcat, portal culling and multiple floors afterwards.

## Recommendations
- [TONIGHT] Generator core: 1 m integer grid, thin walls on cell edges. Corridor lattice: corridors 2 m wide; the 2 outer vertical lines and all horizontal lines are full length; inner vertical lines are absent 20% / partial 35% / full 45% of the time. Blocks between corridors are cut into rooms by BSP (minSide 3, maxSide 8, maxArea 48, stop chance 0.35), with a 12% chance of keeping a 40-220 m2 block as one big hall. Perimeter strips 4-7 m deep give exterior rooms for the entrance and fire exit. -- Prototyped and tested: guaranteed loops for escaping (cyclomatic number p10=23 at 64x48), natural chokepoints, plausible facility/hospital floor plans, and everything is a rectangle, so floors, ceilings, culling and room lookup are trivial. About 450 lines of TS, no authored assets.
- [TONIGHT] Door pass after layout. Corridor-to-corridor edges are open. Each room gets a primary door on its longest corridor run, at least 1 cell from the run ends; double door (len 2) if area >= 48 and the run is >= 5. Second door if area >= 30 or at a 15% chance. Rooms without corridor access get a door to a connected neighbour room (suite). Extra room-to-room doors at 12%. 25% of junction openings become closable fire doors. 12%+10%*difficulty of corridor openings become rubble, only if the level stays connected. -- Second doors and room-to-room doors add escape routes through rooms. Fire doors break the long lattice sightlines and attenuate sound, so closing doors is a stealth tool. Rubble adds chokepoints without breaking connectivity.
- [TONIGHT] Locks and keys as nested zones: grow a BFS ball over the full room+corridor graph from the entrance (45% of spaces, then 50% of what remains). The largest leftover component becomes the next zone. Exactly one boundary door gets locked (keycard colour z, preferring corridor-to-corridor doors); the rest become blocked. Put key z in a zone z-1 room, maximising graph distance from the lock plus a 15 m bonus for dead-end rooms. Confirm with a solvability loop that collects keys and expands reachability until nothing changes; on failure retry with seed#n (max 10). -- Solvable by construction (Metazelda key-level invariant), works on any graph, about 60 lines. Unexplored-style lock-and-key cycles happen naturally because each zone still contains loops. Prototype: 0 unsolvable levels in 1000 seeds; 0.8% get fewer zones than requested.
- [TONIGHT] Server-authoritative level: the server (Node) generates the layout and broadcasts LevelLayout JSON (spaces, doors, items, genVersion, layoutHash) on round start. Clients build meshes from the JSON. Seeds are used only for reproducing bugs and for cosmetic decoration (clutter, decals), via per-space streams makeRng(seed,'decor:'+id). -- 22 KB raw / 4.6 KB gzip, so sending it is trivial. Removes all cross-engine determinism risk (a friend on Firefox, Math.sin differences, generator version skew) while keeping seed-based reproducibility.
- [TONIGHT] PRNG: write xmur3 (string hash, used for seeding) + sfc32 in about 25 lines, no dependency. Use one stream per stage: `${seed}|${GEN_VERSION}|${stage}` for layout, doors, zones, place and decor. Only integer, Manhattan or squared distances in gameplay-relevant generation; always give sort comparators an id tie-break. -- sfc32 passes PractRand. mulberry32 is known to skip a third of 32-bit outputs. seedrandom has not been published since 2022. Per-stage streams keep layouts stable while placement code is tweaked (verified: adding draws to the zones stage left the layout unchanged).
- [TONIGHT] Placement rules: objectives chosen by farthest-point sampling on graph distance, at least 1 in the deepest zone, count 3+round(3*difficulty). One teamwork switch pair in the same zone, >= 18 m apart. Loot per room floor(area/14*(0.5+depth)+rand), value scaled by depth. Hiding spots: 30% of rooms, plus lockers in any corridor more than 16 m (graph distance) from the nearest hiding spot. Lights: ceil(area/24) per space, off with p=0.08+0.15*difficulty+0.08*zone, flicker with p=0.1+0.1*difficulty. Vents in rooms with dist >= 55% of max. Fire exit in the deepest zone's perimeter room (fallback to lower zones, dist >= 40% of max). -- Each rule is a few lines over the space graph, scales directly with difficulty, and enforces risk/reward (deeper means more valuable and darker) and survivability (hiding-spot coverage). All placement items are prototyped.
- [TONIGHT] Server AI over the same edge grid: wallV Uint8Array((W+1)*H) and wallH Uint8Array(W*(H+1)) (0 free, 1 wall, 2 door, 3 blocked) plus door-id arrays. 4-neighbour A* with a door cost of +2 (flatqueue 3.1.0). Line of sight by Amanatides-Woo grid traversal, checking each crossed edge. Hearing by a Dijkstra flood with budget = loudness in metres: open door +1, closed door +6, walls block. -- Measured in Node: A* across the map 0.17 ms, 100k LOS rays 4.8 ms, sound flood 0.04 ms. Deterministic, unit-testable, and door open/close/lock takes effect instantly with no navmesh rebuild.
- [TONIGHT] Feed voice-chat loudness into hearing: clients send mic RMS (AnalyserNode) as noise events 5-10 times a second. The server floods sound from the speaker's cell, and monsters investigate the cell where the sound arrived, i.e. the doorway (Hitman/Thief style: sound seems to come from openings). -- Makes proximity voice a stealth mechanic (Lethal Company's Eyeless Dog reacts to voice) at negligible cost, because only numbers go to the server.
- [TONIGHT] Geometry: one bucket per space and material. Floors and ceilings are 1 quad per space rect. Walls are edge runs trimmed by T/2 at each end, with 'posts' at every grid vertex touched by a wall, and post faces emitted only where no wall continues. No top or bottom faces. Lintel plus soffit above doors. World-space UVs (u = x or z in metres / 2 m tile, v = y / tile). Merge per space with mergeGeometries(geos, true) and a material array. InstancedMesh for door frames, doors, lockers, props, light fixtures and decal quads. -- No seams or z-fighting at corners, T-junctions or door jambs without per-corner special cases. Prototype: 10.2k triangles, 4.5 ms warm build for 64x48. Faces belong to the space they face, so culling per room works directly.
- [TONIGHT] Culling: DunGen-style adjacency culling. Find the camera's space with owner[floor(z)*W+floor(x)], BFS through doors whose isOpen is true up to depth 3, set group.visible, and zero the intensity of lights outside the visible set. Add a door-rectangle screen-space portal test later. -- DunGen documents adjacency culling as stable-cost with 'cull behind closed doors'. It bounds draw calls (about 710 space x material buckets per level, about 60-120 visible) and the cost of dynamic lights.
- [TONIGHT] Lighting hooks (coordinate with the graphics researcher): room and corridor lights are non-shadow PointLights under three r186 ClusteredLighting (Forward+, up to 1024 lights). Keep the light count constant and flicker or break lights by changing intensity. Only player flashlights (SpotLight) cast shadows. Optionally bake a LightProbeGrid, or voxelize VXGI once at level load, since the level geometry is static. -- Read in the r186 source: ClusteredLighting only clusters point lights with castShadow false. DynamicLighting exists to avoid material recompiles when the light count changes. VXGI suits static procedural geometry but skips BatchedMesh, so use Mesh/InstancedMesh.
- [TONIGHT] Agent test harness: a CLI `node tools/gen-cli.ts --seed X --png` (Node 24 runs .ts natively). A 1000-seed property test asserting no throw, unreachable==0, solvable, loopsZone0>=3, hiding coverage, fire exit present, and generation under 10 ms. Golden layout hashes for fixed seeds (bump GEN_VERSION when the generator changes on purpose). Dependency-free PNG map render for agents to view. -- No human to look at levels in an editor. The prototype's PNG renderer and invariants caught 2 real bugs (zones splitting the corridor graph; infinite loot at non-finite distance) within minutes.
- [later] Theme presets from the same generator: facility (lattice + halls + vents); hospital (corridor width 3, full outer lines, inner lines mostly absent, so a ring corridor with double-loaded 4x5 wards and 2x2 bathroom suites); house (footprint 20-30 x 14-20, 1-2 corridor lines, maxArea 30, 35% room-to-room doors, open living/kitchen edges). -- Different looks from parameter changes only. Facility first tonight.
- [later] navcat 0.4.1 (pure JS, MIT, runs in Node) as the navigation upgrade, for furniture-aware smooth movement and multiple floors: generateSoloNavMesh with cellSize 0.15 and walkableRadius 0.25-0.3. Doors via markBoxArea door areas plus a custom QueryFilter.passFilter (as in the official doors-and-keys example), crowd API for agents. recast-navigation-js 0.43.1 (WASM) only if build or query speed becomes a problem. -- Measured navmesh build 100-330 ms for 64x48 m. navcat's own benchmark puts recast's WASM build at about 2.5x faster, but it needs async init (about 40 ms) and manual destroy(). Not needed while the AI lives on the edge grid.
- [later] Deferred: DunGen-like doorway-socket module stitching for hand-designed set-piece rooms, Unexplored-style cycle templates (alternate dangerous route, one-way shortcut), WFC, multiple floors with stairwells, corridor jogs to break sightlines. -- Each needs authored content or a lot more code. Add them once the core loop is fun.

## Risks
- Lattice layouts look too regular and have very long straight sightlines (60 m corridors), which can make stealth either trivial or unfair. => Fire doors on 25% of junction openings (already prototyped), partial or absent inner lines, 12% big halls, rubble; later corridor jogs (offset segments by 1-2 cells), cross-shaped halls, and set-piece rooms stamped from JSON templates. Vary block sizes per theme.
- Client and server generate different levels (Firefox libm, generator version skew, JIT float differences). => The server generates and sends the layout JSON (about 5 KB gzip). Clients only build meshes and seeded cosmetics; GEN_VERSION and the layout hash are in the message; no transcendental Math functions in generation.
- Zone growth occasionally makes fewer zones than requested (0.8%), or puts a locked wing right next to the entrance, which can feel odd. => Accept fewer zones, or retry with seed#n until zones == locks; add a scoring pass that rejects levels whose lock door is under 10 m from the entrance. Show keycard colours on the in-game terminal map.
- Seams or z-fighting at wall corners, T-junctions and door jambs in generated meshes. => Runs trimmed by T/2 plus vertex posts that emit only exposed faces (prototyped); world-space UVs hide seams; an agent screenshot test (Playwright) of 5 fixed seeds from 4 camera positions each.
- Draw-call explosion (about 710 space x material buckets per level) or many dynamic lights killing frame rate on friends' mid-range GPUs. => Adjacency culling depth 2-3 with lights tied to room visibility; ClusteredLighting for non-shadow point lights; shadows only on flashlights; reduce room density for early days (BSP maxArea 48 to 80). Merge per block instead of per space if the draw-call count is still too high.
- Using BatchedMesh for level geometry silently excludes it from VXGI. => Use plain Mesh per space plus InstancedMesh for props (VXGI handles isInstancedMesh). Exclude dynamic doors from voxelization.
- Navmesh disconnects at 1 m doors if navcat or recast is adopted with coarse voxels. => Use edge-grid nav tonight. When switching, use cellSize 0.15 with radius 0.25 and add a test asserting every room centre is reachable on the navmesh.
- Generator bugs only visible as unfun levels (keys too far, dead-end traps, objectives clustered). => Property tests on metrics (loopsZone0 >= 3, key-to-lock distance cap, objective spacing >= 12 m) plus PNG renders reviewed by agents. Log seed+GEN_VERSION per round so friends can report "seed X was broken".
- Too many tiny rooms (about 140 at 64x48) make levels mazy and slow to loot. => Tune BSP (minSide 4, maxArea 60-80, stop chance 0.45) and raise the hall chance for the facility theme. Measure rooms per 100 m2 in tests.

## Decision-critical claims
- Sending the full server-generated layout is cheap: measured 22,431 B JSON / 4,626 B gzip for a 64x48 m, 140-room level, so client-side regeneration from a seed is unnecessary for gameplay state.
- Edge-grid A*, LOS and sound flood are fast enough for authoritative monster AI in Node: measured 0.17 ms per cross-map A*, about 50 ns per LOS ray, 0.04 ms per 30 m sound flood.
- navcat 0.4.1 is pure JS and runs in Node; solo navmesh build for 64x48 m takes 100-330 ms at cellSize 0.1-0.15; 1 m doors disconnect at cellSize 0.2 with radius 0.25 (measured).
- The lattice+BSP+zones generator produced valid, solvable levels for 1000/1000 seeds (0.4% needed one retry) in 1.6 ms p50 at 64x48 (measured, prototype in scratchpad).
- ECMAScript Math.sin/cos/exp etc. are implementation-approximated (only sqrt, imul and basic arithmetic are exact) and Firefox uses fdlibm only with resistFingerprinting, so seed-only regeneration across browsers is not guaranteed bit-identical.
- three.js r186 includes ClusteredLighting (non-shadow PointLights only), DynamicLighting, LightProbeGrid (WebGPU bake) and VXGI; VXGI skips BatchedMesh.
- Lethal Company interiors use DunGen doorway-socket tile stitching (medium confidence, community sources); its approach depends on authored tile prefabs, which this agent-only project cannot cheaply produce.

## Open questions
- Single floor tonight, or are stairs/elevators needed (which would push toward navcat with off-mesh links, or per-floor grids with stair links)?
- Which theme ships first: research facility (prototyped), hospital, or house? This picks the parameter preset and room-type vocabulary.
- Monster roster: which monsters can open doors, use vents (vents as graph shortcuts), see in the dark, or hear voice? This sets door costs, the vent graph and perception parameters.
- Target round length and map size per day (Lethal Company-style quota days?), which tunes W/H, room density and lock count.
- How Claude/LLM content plugs into procgen: per-room lore notes, terminal logs, codes for keypads, or theme/mission briefs selected from Items. The placement code should expose item slots (noteSlots) for it.
- Physics/collision choice (Rapier vs custom AABB-vs-edge-grid) is owned by another researcher; player collision can reuse the wall boxes from navgeo.ts.
- The web search budget ran out before Lethal Company's DunGen usage (seed sync, RoundManager.GenerateNewFloor) could be confirmed from primary or modding docs; it rests on community sources (medium confidence).
